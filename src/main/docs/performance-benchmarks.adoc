=== Single-thread byte-array hashing

Each invocation hashes a reused byte array and returns the result to JMH.
The 8 KiB run measures throughput. A separate 8-byte run measures average time per call after warm-up.
Each fork fills its array from the same fixed seed. The `xx128low()` method returns the low 64 bits of XXH128.

Measured on 23 November 2026 with JMH 1.37 and Ubuntu OpenJDK 21.0.13.1 on an AMD Ryzen 9 9955HX3D, Ubuntu 24.04.5 LTS (Linux x86-64).
The JVM and its one benchmark thread were pinned to isolated logical CPU 4 on the chiplet with 96 MiB of shared L3.
The CPU frequency governor was `performance`, with boost enabled and a reported maximum of 5.46 GHz. No additional JVM options were set.
Each function and input size used three fresh JVM forks, each with three 1-second warm-up iterations and five 1-second measurements.
Errors are JMH's 99.9% confidence interval half-widths. Multiply 8 KiB ops/ms by 0.008192 to obtain decimal GB/s.

The link:ryzen-9955hx3d-jmh.csv[per-iteration JMH scores] give the five measurements from each fork in their original units.

Run from the repository root on Linux with Maven and a JDK. Select an available logical CPU on the host.

[source,bash]
----
mvn test-compile dependency:build-classpath -Dmdep.includeScope=test -Dmdep.outputFile=target/jmh-classpath
cpu=4
classpath="target/test-classes:target/classes:$(cat target/jmh-classpath)"
benchmark='net\.openhft\.hashing\.LongHashFunctionBenchmark\..*'
taskset -c "$cpu" java -cp "$classpath" org.openjdk.jmh.Main "$benchmark" -p inputBytes=8192 \
  -t 1 -foe true -rf json -rff target/long-hash-results.json
taskset -c "$cpu" java -cp "$classpath" org.openjdk.jmh.Main "$benchmark" -p inputBytes=8 \
  -bm avgt -tu ns -t 1 -foe true -rf json -rff target/short-hash-results.json
----

=== Measurement Protocol

* Build the library in release mode (`mvn -q verify`) before running any benchmarks to ensure all classes are compiled and tests have passed.
* Pin tests to an isolated core, minimise other system load and report the CPU model and frequency configuration.
* Use a harness that exercises each `LongHashFunction` via the public API (for example, `hashBytes(byte[])`) over representative buffer sizes.
Warm up the JVM until results stabilise before sampling throughput.
* Record:
** *Speed (GB/s):* sustained throughput while hashing large buffers in steady state.
** *Bootstrap (ns):* per-call overhead measured on very small inputs (e.g., empty or sub-cache-line data).
* Capture both native and non-native endianness where practical; conversion overhead on big-endian systems should be noted if it materially deviates from little-endian results.

=== Reporting Guidelines

* Update `README.adoc` with the latest benchmark table, noting the hardware, JVM version, and any JVM flags used during the run.
* Mark missing measurements explicitly.
* When an optimisation changes algorithm behaviour or memory access, include before/after data in the pull request description so reviewers can confirm the impact.
* Archive raw benchmark logs alongside the pull request or link to them from the decision log to ease future regression analysis.
